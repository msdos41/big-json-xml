# Search after the scan runs on its own thread and jumps between candidates

A text search started after the scan has completed runs on its own thread. It reads the file through a second, independent reader and keeps its own parser state, so the window's pump only hands its hits over. A hit is handed over only once its path can no longer change: XML holds back a hit inside an element that is still open, and a hit that would be renamed when a root field turns into a list. Hits therefore arrive in document order with the same paths, offsets and lengths as a search on the pump, and Find Next and Find All see the same sequence. Esc, a new search, closing the document, and Find Next keep their meaning: a new search or cancel stops the thread, and Find Next waits for the next hit. A short document is still searched at once on the caller. A search started while the scan is running stays on the pump under ADR 0051, and so does any source that cannot open a second reader.

When every hit must contain the needle's own bytes, the search reads ahead with a vectorized byte search and jumps over list entries with no candidate. This holds for a case-sensitive needle of printable ASCII. JSON also stops at any backslash, and XML at any entity reference, CDATA section, namespace declaration, and any tag that could split the needle's text. The jump uses the list-entry offsets: JSON's from the scan (ADR 0024, ADR 0052), and the XML root list's from a byte search for its entry tags, used only when it finds exactly as many as the scan counted. Skipped entries are counted, not read, so every later path keeps its index. Each look-ahead reads a bounded window, so cancel is noticed quickly.

This supersedes two clauses of ADR 0049: "Extra threads stay out until this single-threaded walk has nothing left to give up", and "text search still does not read the list-entry offsets". A resident search index stays rejected: nothing is kept per hit or per word, and the XML root offsets are the same packed store a list already keeps. Memory-mapped reads were measured against plain reads for the byte search and were within a few percent on a warm cache, so reads stay as they are (ADR 0052).

A search that is not case-sensitive, or whose needle is not plain ASCII, still parses every entry. It no longer blocks the window, but it takes as long as before.
